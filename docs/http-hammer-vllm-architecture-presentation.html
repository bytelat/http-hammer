Architecture Walkthrough

Explaining http-hammer against a vLLM-style serving stack

The simulator creates realistic HTTP load from a dataset, controls rate and concurrency, and measures how the server path behaves from the API boundary down to the engine.

http-hammer Load generator: dataset, request templates, RPS control, workers, pings, metrics.
APIServer HTTP surface: accepts OpenAI or recommender routes and translates requests into engine work.
Core Engine Execution layer: schedules model work, uses KV/cache state, and returns generated or ranked output.

Main Idea

http-hammer is outside the model server

It does not run inference. It simulates clients and stresses the HTTP serving path with controlled request flow.

Dataset Parquet rows: chat messages or recommender prompts.
http-hammer Builds JSON bodies, schedules requests, keeps sockets alive.
vLLM Server Receives HTTP requests and performs model serving.
Presenter note: frame http-hammer as the test client. The server can be local, remote, or behind an SSH tunnel; the hammer only needs an upstream host and route.

Inside http-hammer

Config JSON upstreams, routes, model, body_fields, template, concurrency, keep_alive
Dataset Loader Reads Parquet and maps columns into request body fields.
Injector Uses current RPS to enqueue request indexes and periodic pings.
Workers Own connection pools, send HTTP/1.1, parse responses, update stats.
UI Thread Changes runtime RPS and displays health, rate, latency, connection state.
Metrics Collector Polls the server metrics route and pushes observations into the UI.
Logs and Histograms Request latency, ping latency, sent/received rate, OK/error counters.

vLLM Drawing

APIServer and Core Engine responsibilities

HTTP Client http-hammer sends POST requests and ping checks.
APIServer Owns HTTP routes, request validation, protocol translation, streaming/result formatting.
Async Engine Client Bridges serving code to engine execution and request lifecycle state.
Core Engine Schedules decode/prefill work, manages execution state, coordinates model workers.
Inside the engine boundary
Scheduler Selects which requests run next.
KV Cache Manager Tracks memory blocks and reuse.
Model Executor Runs model kernels and produces logits/tokens.
Presenter note: APIServer is the HTTP/API owner; Core Engine is the execution owner. http-hammer exercises both by pushing controlled traffic through the same front door real clients use.

End-to-End Test Path

What happens during a hammer run

1. Load rows Parquet data becomes a vector of JSON request bodies.
2. Shape traffic RPS and concurrency determine enqueue pace and open sockets.
3. Hit APIServer Requests enter /v1/chat/completions or /recommend.
4. Stress engine Server scheduling, cache, model execution, and result formatting are exercised.
5. Parse response Workers wait for complete Content-Length responses.
6. Record latency Request and ping histograms are refreshed each second.
7. Observe limits Throughput, errors, pings, and metrics reveal bottlenecks.

How to Explain the Value

http-hammer answers operational questions

  • Can the APIServer keep accepting requests at the target rate?
  • Does the Core Engine fall behind when beam search or recommender traffic increases?
  • Are pings and metrics still healthy while real requests are in flight?
  • Which part changes first: latency, errors, free connections, or server metrics?
Presenter note: this is the bridge from diagrams to a live demo. Start with low RPS, raise it, watch pings and request latency, and explain that the hammer is making pressure visible.
